# GitFit — notes for Claude

## What this is

GitFit is a personal gym tracker for one person (Rex), used mainly on an **iPhone in Safari, added to the home screen** as a web app. You create workouts (title + exercises) that make a **rolling cycle** (Push > Pull > Legs > Push …, not tied to weekdays; version 14 replaced the weekday plan at the user's request), log sets during a workout (and can swap an exercise for today only), and see progress:
- **Workouts tab** (`Views.home()`), top to bottom: the in-progress banner; a **This week** card (flame + streak count: the flame is green whenever the streak is above 0, gray only at 0, at the user's request, so mid-week doesn't look like a lost streak; "2/4 workouts", replaced by a green "Week done ✓" once the week is hit; and Mon → Sun cells: a day with a finished cycle workout shows a short label from its name, `workoutLabels()`: first letter, more letters if an earlier workout in the cycle has it, so Push P, Pull Pu, Legs L; two in a day "P/L"; quick workouts aren't shown; today outlined, days to come dimmed; days change at 3 am, `appDay()`, `Streak.weekDays()`; tapping a day with a workout opens Past workouts on that day); **Next Up** (the next workout in the cycle on a big card, with its small cycle number, "5 exercises · last done 3 days ago" / "never done" and Start workout; a workout in progress takes this card's place as "In progress" with its timer, sets so far and Resume, one card and not a separate banner); **Then** (the rest of the cycle as rows in the order it's coming, each with its small gray number in the cycle, the same as Edit cycle's, so it's clear where the cycle starts, the user's request; tapping a row opens that workout's screen, where Start is; the "Edit cycle" link is on this heading; with only one workout it has "+ Add your next workout"; during a quick workout it starts with Next Up itself, tagged "Next"). This replaced the "Do a different workout" link and sheet after a usability test: the user picked it over showing every workout the same size. Then **Today's cardio** (checkbox rows). With no workouts, Next Up's card has a "Create your first workout" button. The app always opens at the top. New workouts are made in a pop-up that only asks for the title (`Views.newWorkoutDialog()`; Back from the new workout returns to where it was made), from Edit cycle → + New workout or the + button's Planned workout. Past workouts link at the top. Profile keeps the full streak card too (its flame follows the same rule: green above 0, gray at 0).
- **The + button** is in the tab bar, between Cardio and Log, in the middle of the five (the user's choice of place; it was a floating button on the Workouts tab before), so it's on all four tabs' main screens (`tabs.js`: `addButtonHtml()`, `ADD_OPTIONS`). The user wants it to stand out and not look like another tab: a solid green rounded square with a black plus, no label, sitting level with the tabs (it was raised above the bar before; the user didn't like that). Tapping it opens a menu just above the bar, centered over the + (the page behind darkens, the plus turns to a ✕, tapping anywhere closes it) with, in the user's words: **Quick workout**, **Quick cardio** (the + Add cardio form), **Planned workout** (with more than one split it first asks "Add it to which split?", `Views.workoutSplitPicker()`, a full split can't be picked; then the usual New workout pop-up, which makes it in that split without switching you to it), **Planned cardio** (the new planned cardio form) and **New split** (the Create split pop-up; the new split becomes the one you're on and Edit cycle opens for it). A plan or one-off cardio saved away from the Cardio tab shows a short message, since it may not appear on that screen.
- **Edit cycle** (`#/cycle`, `Views.cycleEdit()`): the name of the split you're on with a **Switch cycle** link on its right (see Splits below), then the cycle as numbered cards (the next one marked; ✕ on each place; tap one to open its screen, and Back returns here via `returnStack`; hold and drag to reorder), + New workout (wide), + Repeat a workout (the same workout in the cycle another time) and + Add rest day, then **Planned sets per cycle** (muscle rows under group headings, each opening to the exercises behind it).
  - **Splits** (version 15, the user's request: "multiple cycles set up and easy to switch between"): `Store.data.cycles` is a list of splits, each `{ id, name, items }` with its own cycle and **its own workouts** (not shared, the user's choice: changing Push in one split never changes another), and `activeCycleId` is the one you're on (`Store.activeCycle()`). "The cycle" everywhere means the active split's items. The Workouts tab, Edit cycle, Next Up and planned sets go by the active split; history, logs, maxes, the map, actual sets and the weekly streak count every split. **Switch cycle** (top right of Edit cycle) opens a small pop-up, not a screen (`Views.cycleSwitcher()`, `showSplits()` in `app.js`): "Your splits", one row each with its workouts' names (the one you're on has a "Selected" badge; tapping another switches, and the pop-up stays open so Done closes it), a pencil on each row (`Views.cycleDetails()`: name, Done, Delete split), + Create split and Done. The wording is the user's: the link says "Switch cycle", the things in the pop-up are "splits". **Create split** asks for a name, then Start empty or Copy <the split you're on> (the user's choice; `Views.newCycleDialog()`, `Store.addCycle()`): a copy gets its own copies of the workouts and the new split becomes the selected one. **Each split has its own Next Up**, and switching back carries on where it was left (the user's choice): every finished planned workout saves its split (`session.cycleId`, from `Store.cycleOf()`), and `lastCycleIndex()` only looks at that split's sessions. A workout in progress carries on if you switch (the big card shows it with no cycle number). Delete split deletes its workouts (asks first, history stays) and the last split can't be deleted, so there's always one. A split with no workouts has the Edit cycle link on the Workouts tab's Next up heading while there are other splits, so you can always switch back. Data from before version 15 becomes one split named "My split" (`DEFAULT_CYCLE_NAME`).
  - **The cycle** (`Store.cycleItems()`, the places of the split you're on): an ordered list of places, each a workout (`workoutId`) or a rest day reminder. A workout can be in it more than once (the same workout, not a copy), up to 7 workouts (`MAX_CYCLE_WORKOUTS`). Every workout is in the cycle: removing a workout's only place deletes it (asks first); Delete workout removes all its places. Rest days are only reminders, at the user's request (they don't use them): Next Up never says Rest, it skips them and shows "Rest day planned before this one".
  - **Next Up** = the place after the most recently finished planned workout (`Store.lastCycleIndex()`), always worked out from history, never stored. Each session saves the place it was done as (`cycleItemId`, chosen by `Store.cyclePlaceFor()`: the place it was opened from, `#/workout/<id>/<cycle item id>`, else the first place with that workout from Next Up on). If that place is gone, it falls back to the workout's first place, else the start of the cycle. Quick workouts don't move it. Any finished workout moves it, however many sets were logged.
  - Tap a workout to open its screen (`Views.workoutPreview()`), which is both the look at it and the place to change it, with no separate edit screen (the user's choice): Start workout (no pop-up unless another workout in progress would be discarded, at the user's request) and a pencil on top (a pop-up with title, Done, Copy workout and Delete workout, `Views.workoutDetails()`), then one short row per exercise (target, and last time's sets on one line) with a down arrow so it's obvious it opens (the user asked for that); tapping it opens last time's sets in full, the note, Edit and Log (`openPlanEx`, toggled with a class, kept when Back returns from a log). Edit opens the exercise's sets & reps, Change exercise, Save, Cancel and Delete inside its card. Then + Add exercise (the search stays open to add several, and marks ones already in the workout "✓ Added"; a new workout opens with it ready and no Start button). Hold and drag a row to reorder it: while held, every row shrinks to its name (`body.is-reordering`, the user's choice). A thin planned sets strip is pinned to the bottom (`plannedStrip()`): one line of numbers, the muscles the last edit changed first in bold white, and tapping it opens the full list with a switch between this workout and the whole cycle.
  - **Quick workout** (`#/quick`): a one-off workout not added to the cycle — editable title, + Add exercise (its search can also create a custom exercise, `quickAdd.creating`), 1 set each with + Add set and − Remove set, no targets; saved as a session with `quick: true` (no workoutId, empty plan), counted for logs, maxes, the map and actual sets, shown in Past workouts with a blue date and a Quick tag. It doesn't move Next Up or count toward the streak.
  - Removed in version 14 (all date-based): the Mon–Sun week, day chips, drag to another day, Done/Partial/Missed, Catch up, Missed this week, quick-workout makeup sets, and the suggested set ranges (the user found them annoying and plans a coaching-style overhaul later). Don't bring them back unasked.
- **During a workout:** a bold white timer in the top bar and an "In progress" strip with sets so far; each set's number turns into a green ✓ once its reps are typed (`setNumber()` in `views.js`, `refreshSetNumber()` in `app.js`, no redraw); the open exercise is surface-2, the others surface-1; the first unfinished exercise opens by itself; holding an exercise's heading row and dragging reorders it, for the user to fix an order they've realized is better, so on a planned workout it saves permanently to the plan with an "Order saved" message (`#exercise-list`; on a quick workout it's only for that workout, and an exercise added for today stays below the list); a Next button appears once an exercise is filled in (the last one says Done), and if every set hit the top of its range a small message suggests going heavier (`Store.readyForMoreWeight()`). + Add exercise for today (`draft.added`, `ex.today`) is logged but isn't in the plan. Each exercise has one note (`exerciseNotes`, kept until changed) and a Log button; Back from a log returns to where it was opened, as it was left (`returnStack` in `app.js`).
- **After finishing:** a summary (`Views.summary()`, `Store.sessionSummary()`) with time, sets, weight lifted, new bests (only if there are any, each opening its log; a first-ever exercise doesn't count) and workouts this week. It's kept in memory only (`summary` in `app.js`): it stays on the Workouts tab until Close or until the app is fully closed. The user asked for this.
- **Planks are timed** (`TIMED_EXERCISES` in `library.js`, just planks, at the user's request): seconds are saved as the set's `reps`, the weight box shows a locked "—", and the log shows the longest hold instead of an estimated max. Growth uses the longest hold (40 → 50 sec = +25%).
- **Cardio** (`cardio.js`): much less strict than lifting, at the user's request: it only adds to their record. Nothing turns red, nothing says Missed, and it never touches the weekly streak, the cycle or planned sets, so keep it out of `streak.js` and `stats.js`. Doing it happens where you lift (checkbox rows, Quick cardio in the + menu); the **Cardio tab** (`#/cardio`, `Views.cardio()`, the user's choice, because more cardio features will go there later) is for planning and looking back. **Planned cardio** (on the Cardio tab) has a type, optional name and optional numbers, on picked weekdays or **After every lift** (`afterLift`; it was "every lifting day" before version 14). Weekday plans show as checkbox rows under **Today's cardio** on the Workouts tab, with anything else logged today (`Cardio.rowsFor()`); After every lift ones show above Finish on every workout, quick ones too (`Cardio.afterLiftRows()`), because the user wanted to check them off at the end of each lift. One tap saves an entry with the planned numbers, unless they don't meet what an entry needs (minutes, or distance + time on a run; `Cardio.isComplete()`). Then a short pop-up asks for only the time and distance that weren't planned (`Cardio.missingFields()`, `form.quick`): no name, type or date, at the user's request, because checking off should be quick. The full form is for + Add cardio and tapping a checked row. A run's distance has tappable buttons (`RUN_DISTANCES`: 1 mile, 5K, 10K, Half, Marathon, at the user's request, so race distances needn't be typed in miles): one fills in the distance and names a nameless run ("5K run"; a name typed by hand stays, and typing another distance clears a button's name), and a planned run with no time only asks for the time. A checked row opens its numbers with Uncheck (deletes the entry, no question). One-offs, and entries whose plan was deleted or changed, also show as checked rows that day, with Delete (asks first) instead. Entries keep their own copy of the numbers. **+ Add cardio** (Quick cardio in the + menu, and the Cardio tab) allows any past date, unlike lifting, and never a future one; a new entry is dated by the 3 am day. **The Cardio tab**, top to bottom: "This week: X sessions · Y min" (no goal), + Add cardio, planned cardio (above the calendar since the entry list keeps growing), **Run times** (a graph with a switch between 1 mile and 5K, `Views.cardioGraph()`, `RUN_GRAPHS`, the user's choice of distances: the latest time big, the best on a line only when the latest isn't it; runs within 2% of the distance count, treadmill or outside, `Cardio.runsOf()`; tapping a dot scrolls to that day on the calendar with its entries showing), a calendar matching the exercise log's, and every entry newest first with Edit and Delete. Ideas the user set aside for later: pace groups, more charts, a list of bests; not wanted for now: calories, GPS, Apple Health.
- **Past workouts** (`#/history`): a month calendar of the days with a finished workout (history only, nothing is scheduled on it; days change at 3 am like the week strip; tap a day to list its workouts, `historyState` in `app.js`), then every finished workout grouped by week.
- **Log tab** (`#/log`, a book icon in the tab bar right of the +, the user's choice; it was a Log button on Profile before): the exercise Log (a list of what you've logged; estimated max graph with 3 months / 1 year / all time, "+12% since Aug 3" over it and tappable dots; calendar, a day's sets with a link to the full workout; then a list of every time it was done, each opening that workout. A "Best ever" line only shows when the latest isn't the best, and "Actual 1-rep max" only once one is logged, because the user didn't want it cluttered).
- **Profile tab:** a backup reminder (no backup in 30 days), the weekly streak card, a body weight card (where it's entered after the first-time setup, which also asks for it; it's not in Settings; each change is logged by day and graphed, `bodyWeightLog`; its Body weight log button opens `#/body-weight`, a list of every weight and date with Edit and Delete, and the current body weight is always the newest entry), a front/back muscle map (Growth and Level modes), and **Actual sets, last 7 days** (`Stats.actualSets()`: logged sets per muscle over a rolling 7 days, quick workouts included, 1 primary / 0.5 secondary, each exercise opening its log; the user may rework this once they've used it)
- **Exercise search** shows muscle group chips and recent exercises before you type. **First-time setup** (`Views.setup()`, `settings.setupDone`) shows on a brand new or fully deleted app; workouts per week starts at 4. Sex starts unpicked (`settings.sex` null; older saved data keeps its 'male'), and the map's Level mode asks for it until it's picked in Settings. **Custom exercises** are listed in Settings and can be deleted: they're only marked `deleted`, so history keeps their name, and they come out of search and every workout.
- The user decided against a rest timer, a warm-up set feature, keeping the screen awake, and logging forgotten workouts on past dates. Don't re-suggest them.

The user is not a programmer. Explain changes in plain words, keep the code simple and well commented, and test changes in the browser before calling them done.

## How the user likes to work

- For a new feature, the user often writes a spec and asks you to **read the code, explain the plan in plain words and ask about anything unclear before building**. Don't write code until they say go. Ask only about real gaps, give a recommended answer for each, and re-explain a question in simpler words (with an example) if they don't follow it.
- When a request would change an agreed rule (e.g. how freezes are earned), confirm the rule change first instead of guessing.
- Keep the UI clean: small polish requests are common (removing a marker, hiding a button once it's no longer needed). The look is the dark "Mono" theme (see Key rules), but the user wants everything readable: keep controls and text clear, don't dim things to make them "quiet".
- After finishing, say what changed, how it was tested, and that it's committed but not pushed.

## Tech and file structure

Plain HTML, CSS and JavaScript. **No build step, no framework, no npm, no server, no accounts.** Every JS file is a plain `<script>` that defines globals (`Store`, `Units`, `Library`, `Stats`, `Views`, …).

```
index.html        Page shell: top bar, empty <main id="app">, tab bar, and the <script> tags
manifest.json     Home-screen "install" info and icons
icons/           Home-screen icon: icon.svg (the source: green dots joined by a climbing line on black) and PNGs drawn from it (180 for iPhone, 192/512 for the manifest)
css/theme.css     The theme: every color, font size, radius, spacing and size as variables ("Mono", data-theme on <html>)
css/styles.css    All styling, using only the variables from theme.css
js/library.js     Muscle catalog (MUSCLE_GROUPS), EQUIPMENT, built-in exercise LIBRARY, search
js/storage.js     ALL saving/loading (localStorage), data shape, upgrades (normalize), export/import, estimateMax
js/units.js       Converts saved units (lbs, inches, miles, mph, feet) to/from the shown unit
js/cardio.js      Cardio types (CARDIO_TYPES), rules and wording; saving goes through Store
js/standards.js   Strength standards from strengthlevel.com for the map's Level mode
js/stats.js       Per-muscle numbers: growth, levels, planned sets per cycle, actual sets in the last 7 days
js/streak.js      Weekly streak rules: week results, freezes, Profile summary
js/bodymap.js     Muscle map drawing and colors
js/tabs.js        Bottom tab bar (Workouts, Cardio, Log, Profile) with the + button and its menu; shows only on each tab's main screen
js/views.js       Builds each screen's HTML; each returns { title, back, html }
js/app.js         Routing by URL hash (#/, #/cycle, #/workout/<id>[/<cycle item id>], #/history, #/cardio, #/profile, #/settings, #/log, …), event handling, and the drag code
README.md         User-facing guide; keep it up to date when you change structure or behavior
```

Rule of thumb: **storage.js** knows about data, **views.js** knows about HTML, **app.js** connects them.

**Script order in `index.html` matters**: library → storage → units → cardio → standards → stats → streak → bodymap → tabs → views → app. A new file goes where its dependencies are already loaded.

## How data is saved

- Everything is one JSON object in the browser's `localStorage` under the key **`gitfit-data`** (`STORAGE_KEY` in `storage.js`). It lives only on that device and that browser — the phone's data and the computer's data are separate.
- The data shape is documented in the comment at the top of `storage.js`: `version`, `settings`, `customExercises`, `workouts` (id, name, exercises), `cycles` (your splits: `{ id, name, items }`, each item a place: `{ id, kind: 'workout', workoutId }` or `{ id, kind: 'rest' }`), `activeCycleId` (the split you're on), `sessions` (finished workouts, oldest first, with `workoutId`, `workoutName`, `cycleItemId`, `cycleId` (the split it was done in) and the workout's `plan` when logged), `draft` (workout in progress, saved on every keystroke, with `cycleItemId` and any `swaps` for today; a quick workout's draft has `quick: true`, `name` and its own `exercises` list), `streak` (start week, week results, `thisWeekGoal`, pending notices). Version 7 turned each old weekday (name + exercises) into a workout on that weekday with the same id, and sessions' `dayId`/`dayName` into `workoutId`/`workoutName` (the "Monday – " part removed). Version 8 added quick workouts. Version 9 added the workout timer: `draft.pausedAt` / `pausedMs`, each draft set's `loggedAt`, and `session.durationMs`. Version 10 added `bodyWeightLog`, `exerciseNotes`, `draft.added`, `settings.setupDone` and `settings.lastBackupAt`. Version 11 added `settings.weeklyGoal` (null on older data, so the app asks once) and `days`/`goal` on new streak weeks. Version 12 made a bodyweight exercise's `weight` only the added weight, and cleared what older sets held there. Version 13 added `cardioPlans` and `cardioLog`; `normalize()` only keeps the fields it lists, so a new list must be added there or it's lost on load and import. Version 14 made the cycle: each workout's `weekday` became its place in `cycle` (Monday first, then their own order within a day) and was dropped, `days` and `streak.locks` were dropped, `session.cycleItemId` / `draft.cycleItemId` and `streak.thisWeekGoal` were added, `weeklyGoal` became workouts a week (same number kept; invalid → 4), and a cardio plan's `everyLiftingDay` became `afterLift`. Version 15 added splits: the one `cycle` list became the first split's `items` (`cycles[0]`, named "My split", with `activeCycleId` pointing at it), and every planned session from before got that split's id as its `cycleId`. A backup counts as valid with `days` (older) or `workouts` (newer).
- Only `storage.js` reads or writes `localStorage`. Other files go through `Store`.
- **Changing the data shape**: bump `DATA_VERSION` and add an upgrade step in `normalize()` so older saved data (and old backup files) still load. Never drop or rename saved fields without migrating them. Update the shape comment at the top of `storage.js`.
- Muscle ids, exercise ids (`refId`) and cardio type ids (`CARDIO_TYPES`) are saved in user data. **Never rename or remove an existing id** without a migration (see `RENAMED_MUSCLES` for how a rename was handled). Adding new ones is fine.
- Finished sessions copy in each exercise's name and muscles so history stays right if the exercise changes later.
- Backup = Settings → Export (JSON file) / Import (`Store.exportBackup()` / `importBackup()`). Imports run through `normalize()` too.

## Key rules

- **The look ("Mono" theme, the user's spec)**: every color, font size, radius, spacing and size is a variable in `css/theme.css` (under `[data-theme="mono"]`, so another theme could be added later; no theme picker yet). `styles.css` and the JS never use their own hex/rgb, shadows, raw radii or font names; the only literals left are the browser bar color in `index.html`/`manifest.json`, the icon in `icons/` and the muscle map legend's color bar. Run a search for those before calling a styling change done.
  - Black background; depth only from surface-1 (secondary containers, the week card), surface-2 (primary cards, list rows, pop-ups), surface-3 (inputs, inactive day cells, segmented tracks, unselected toggles). No borders on cards, no shadows, glows or gradients.
  - **Green (`--success`): text, icons and outlines are accents; solid fills mean "done"** (the user changed this from green-only-for-done). Accents: every text link (Past workouts, Edit cycle, Do a different workout, ‹ Back, Show all, "Log ›": green 600, no underline), the active tab, small icons (ⓘ, gear, chevrons, pencils; ✕ stays gray), chart lines and dots (6px; a new best is 8px with a 2px white ring, from `maxChart()`'s `better` argument: higher for lifts, lower for run times, none for body weight), the Profile weekly progress bar (always green), the streak flame and Week done, calendar rings, and the "Next" badge (green text on `--accent-tint`, radius 6, beside the workout name on Edit cycle). Solid green fills only for done things (completed day cells, set ✓, finished exercise ✓, checked boxes, completed weeks on Profile, the summary ✓, the selected calendar day) plus the one exception, the + button (green with a black plus). Primary buttons (Start workout etc.), segmented controls and selected toggles stay white with black text; secondary buttons surface-3. Red only for destructive actions (transparent with a red border). Blue (`--info`) only for quick workouts and streak freezes; "Rest day" is gray. The muscle map keeps its own color scale (`--map-*`, read by `bodymap.js`).
  - Page titles are 700. "‹ Back" sits on its own row above the title (`body.has-back`, `--header-h` for things that scroll to just under the top bar). Toasts: surface-2, radius 12, 14px padding, 16px above the tab bar, gone after 2.5s (`TOAST_MS`); "Workout saved" with Undo stays 5s (the user's choice). Profile's streak card has no big number next to the flame. The log's "+X% since <date>" sits under the current max, left-aligned, gray.
  - Type: system font, tabular numbers everywhere; section labels are sentence case, 15/600 gray, no ALL CAPS or letter-spacing. Radii differ on purpose: day cells 8, checkboxes 6, buttons/inputs 12, containers and list rows 14, cards and pop-ups 20, + button 14 (a 46px rounded square level with the tabs; it was 18 on 64px while it floated).
  - surface-2 and surface-3 are very close (the user's values), so boxes, unselected toggles and secondary buttons that sit on a card or pop-up use the lighter `--surface-field` (#2c2c2e, the user asked for this; a weak `:where` rule at the end of `styles.css`, so picked/white states still win).
  - The streak flame is two-tone (the user liked the detail): green with a light inner flame (`--flame-core`) while the streak is alive, gray with a lighter gray inner flame (`--flame-off-core`) at 0.
- **Weights are stored in one unit (lbs) and converted for display.** Heights are stored in inches, cardio distance in miles, speed in mph and elevation in feet. The Units setting only changes what's shown. Always use `Units.showWeight()` / `Units.readWeight()` (and the height and cardio equivalents) when showing or reading these — never save kg or km. A cardio box that wasn't changed keeps its saved value, not its rounded display value (`readCardioForm()`).
- **Dumbbell weights are per dumbbell** (the weight of one dumbbell, not both added together). The strength standards in `standards.js` are per dumbbell too; barbell weights include the bar.
- **Estimated max uses the Epley formula**: `weight × (1 + reps ÷ 30)` — `estimateMax()` in `storage.js`. Sets with no weight or no reps have no estimate. Use this function everywhere; don't add a second formula.
- **Bodyweight exercises track added weight** (`Library.isRepsOnly()`; not planks, which are timed): a set's `weight` is only the added weight, null for none (version 12 cleared the body weight older sets held there). The box reads "BW + [ ]" under an "Added weight" heading (`bwBox()`), can be left blank with no warning, and sets show as "BW×10" or "BW+25×8". Sets with and without added weight count as two separate exercises, at the user's request: **max reps** on sets with none (`topReps`; 8 → 10 reps = +25% on the map), and an estimated max of the added weight alone on the others, like any other exercise ("Pull-Up (weighted)" on the map and finish summary). The log has a switch between them for its top card (`logState.weighted`); the calendar and list show every set. Weight lifted adds the body weight of that date (`Store.bodyWeightOn()`).
- **New sets**: a planned set starts with last time's weight. + Add set copies the set above; if that's empty, so is the new one. A weight typed on a set also goes on the sets below it, except any with reps logged (`fillWeightDown()` in `app.js`).
- **Growth on the muscle map** (`Stats.exerciseGrowth()`): over the last 6 weeks, each exercise's best in its first 2 weeks vs. its best in its last 2 weeks, so one bad workout or week doesn't look like getting weaker (the user's choice; they had the old first-vs-latest changed for this). A muscle's percent is the average over the exercises with it as a primary muscle; an exercise counts once it's logged in 3 different weeks. An "i" by the caption explains this (`MAP_INFO` in `views.js`): keep it matching if the math changes. The log's current estimated max still follows the latest workout, on purpose.
- **Tapping a muscle on the map** opens a card under it (`Views.muscleCard()`): its number and the exercises behind it, best first, each opening its log; ones without enough weeks yet; and why a muscle has no number. Level mode lists each exercise's level. It stays when Back returns from a log.
- **Going heavier**: if every planned set hit the top of its range at one weight, a message says so at Next, and next time the exercise shows a white "Try 140 lbs today" (`Store.readyLastTime()`). It's worked out from last time, not saved, and it never changes the boxes (the user's choice).
- **Weight typos**: at Finish, a weight over 1.5× the exercise's heaviest ever and at least 25 lbs more (or over 1000 lbs the first time) asks "Is this weight right?" (`Store.draftWeightChecks()`).
- **Weight lifted** on the finish summary counts dumbbell exercises twice, since their weights are per dumbbell, and shows a whole number.
- **Pop-ups**: always the app's own (`showDialog()`, or `askFirst()` for a yes/no that runs something), never the browser's `confirm()` or `alert()`.
- **Muscle list and set counting**: the muscle catalog is `MUSCLE_GROUPS` in `library.js`:
  - Chest: upper chest, mid chest, lower chest
  - Shoulders: front delts, side delts, rear delts
  - Back: lats, upper back, traps, lower back
  - Arms: biceps, brachialis, triceps
  - Forearms: brachioradialis, forearm flexors, forearm extensors
  - Core: abs, obliques
  - Legs: quads, hamstrings, glutes, adductors, calves

  Each exercise has **primary** muscles (each set counts as **1 set**) and **secondary** muscles (each set counts as **0.5 set**). A muscle can't be both primary and secondary on one exercise. Secondary muscles only affect planned sets: the map's Growth and Level modes use primary muscles only (the user's choice), and the streak's muscle groups go by primary too. Secondary means a muscle that moves a joint under load, or a lower back holding a heavy free bar; grip and general stabilizing aren't listed.
- **Weekly streak** (`streak.js`, rules in its top comment):
  - The weekly goal is `settings.weeklyGoal`: workouts a week, 1 to 7 (default 4), in the first-time setup and Settings ("Workouts per week").
  - A week runs Monday 3 am → next Monday 3 am. A week is hit when its finished workouts (`Streak.workoutsIn()`) reach the goal. Every finished cycle workout counts, in any order, however many of its sets were logged (the user wanted it simple: "log that many workouts"); two in one day count as two. Quick workouts don't count. A workout counts in the week Finish was tapped.
  - A goal change counts from next week: each week is judged against the goal it started with (`streak.thisWeekGoal`, noted the first time the app runs in a week; an unopened week uses the current goal, which can only change while the app is open). Before the first workout is logged, a change counts straight away. Saved on each result (`workouts`, `goal`). This week stays live: it's hit (and celebrates) the moment it reaches its goal, and goes back if a workout is undone or deleted. Profile says "Your new goal of 5 … starts next week" while they differ.
  - Every 4 weeks in a row (streak 4, 8, 12 …) earns 1 freeze (max 2). Hitting the very first tracked week earns one too, so a new user who goes away early keeps their streak (the user's idea); someone whose first week is from before version 11 doesn't get it. A week that ends short uses a freeze if one is held and the streak is above 0, and the streak stays the same. Otherwise the streak goes to 0. (Freezes, the flame, the celebration and 4-week milestones were kept as they were in version 14.)
  - Tracking starts the week the first workout is logged (`streak.start`), and that week counts.
  - Editing or deleting a past workout re-judges its week and every week after it, quietly (no notices; this week only celebrates if it wasn't already hit), each against its saved goal: `Streak.rejudge()`.
  - **Weeks judged under older rules are kept and never re-judged**: version 11–13 weeks counted different days (`days` instead of `workouts`), and pre-version-11 weeks counted sets (`logged`, `planned`, maybe `empty`, no `goal`). A hit already on the week of an upgrade stays too. Only weeks with `workouts` are re-judged.
  - Current, best and freezes are always recomputed from `streak.weeks`; never store them separately.
  - `Streak.update()` runs at the start of every `render()`, when a goal changes, and when the app comes back from the background. A new hit sets `Streak.celebrate`; ended weeks that used a freeze or broke a streak add to `streak.notices`. `showOverlay()` in `app.js` shows them.
  - Profile shows the flame (green while the streak is above 0, gray at 0) with the "3-week streak" headline (no separate big number), "Workouts this week X / Y", best, freezes held, weeks to the next freeze, and a strip of the last 8 weeks + this one. The finish summary shows "Workouts this week" too. The user asked for no marker on the bar.
- **Swap for today** saves the swapped exercise under its own `refId`, with the planned exercise's `exerciseId` and `swappedFrom`, so history stays right. Any swap is fine (no muscle group check since version 14). Before you type, its search lists "Similar exercises" first (`Library.similarTo()`: shared primary muscles, then secondary), then Recent. Its search can also create a custom exercise (`swap.creating`, using the same form and `picker` as a workout's screen), which is then swapped in.
- **Muscle groups** (`Library.groupOf()`, for the search chips): an exercise's group is the group most of its primary muscles are in (tie → the first primary listed), with all 7 groups kept separate (Chest, Shoulders, Back, Arms, Forearms, Core, Legs). Deadlift = Legs, Hammer Curl = Arms.
- **A workout's plan changing while it's in progress**: its screen is the live workout then, with no pencils, so apart from dragging the order this only happens by deleting a custom exercise in Settings. Logged sets are never lost: they stay as an exercise added for today only (`Store.keepLoggedSets()`, `draft.added`); a lower set count keeps them as extra sets (`ensureDraft()`).
- **Tapping something else with the exercise form open** (`withFormSaved()` in `app.js`: Back, Start workout, Log, another pencil, + Add exercise, the top pencil): changes to the exercise being edited save; an exercise only picked so far asks first (Add to workout / Don't add), and so does leaving a custom exercise form with something entered.
- **Adding exercises**: a new one starts with the sets and reps last used for it (`Store.lastTargets()`), and the muscle chip stays picked while adding several (`picker.group`). An exercise's pencil also has a small Move to another workout (`Store.moveExerciseToWorkout()`).
- **Extra sets**: + Add set on a planned workout adds a draft row with `extra: true` (today only, the plan doesn't change; `ensureDraft()` keeps them after the planned rows). − Remove set only takes off extra rows there, never a planned set; on a quick workout it takes off any set but the last one left. The flag stays in the draft and isn't saved on the session.
- **Workout timer**: always worked out from saved times (`Store.draftElapsed()`: now or the pause, minus `startedAt` and `pausedMs`), never a running counter, so it survives closing the app. It starts when Start workout is tapped (or a quick workout is opened) and shows boldly in the top bar of the workout screen, and on the in-progress banner. Leaving the screen doesn't pause it; only the pause button does. Over 3 hours at Finish → "Use last set time" (saves the workout at the last set's `loggedAt`, so it counts for that week; an ended week is re-judged) or "Keep". Duration shows in Past workouts.
- **Planned sets** (the cycle's card on Edit cycle, the strip on a workout's screen, `plannedSetsTable()`): uses `Stats.plannedSets()` (`cyclePlannedSets()` = one time through the cycle; a workout in it twice counts twice), the only planned-sets calculation. Profile's actual sets use the same table with `Stats.actualSets()`. There are no group totals, at the user's request: each muscle has its own row under a heading for its group. A muscle counts every exercise (1 primary, 0.5 secondary). The bars share one scale (the top muscle fills its bar); there are no suggested ranges any more. An "i" explains the counting (`setsInfoBox()`). The cycle and actual sets show muscles with 0 sets; a single workout hides them. Under a muscle, each exercise has one row per workout it's in (planned, opening that workout) or one row saying how many workouts it was in (actual, opening its log). Open/closed rows are kept in memory (`openSets`, `stripRows`, `openActual` in `app.js`, chosen by the table's `data-table`) and toggled with a class, not a redraw, so they slide smoothly.
- **Test data must never be written into the code.** No demo/sample workouts, fake sessions, or seeded user data in any committed file (an earlier `js/demo-data.js` was removed for this reason; `normalize()` still drops any session marked `demo: true`). Test by entering data in the app on the computer, or with a temporary console snippet that isn't committed. Defaults like an empty week are fine.
- **The computer is the dev version; GitHub Pages is the live version.** The live app is https://stevenrecks08.github.io/GITFIT/ (repo `stevenrecks08/GITFIT`, branch `main`). Whatever is pushed to `main` goes live on the phone.
- **Commit automatically after every finished change, without asking.** Use a short, clear commit message.
- **Never push to GitHub unless the user explicitly tells you to** in that message. Don't offer or keep asking to push.
- **Before any push that changes how data is saved** (data shape, `DATA_VERSION`, `normalize()`, ids, storage key, units stored), **remind the user to back up their phone data first** (Settings → Export on the phone) and wait for them to confirm.

## Avoiding breakage

- Test in a browser on the computer: open `index.html` (or a local server), use phone-size device emulation, and check the screens you touched. Check the browser console for errors.
  - Claude's browser pane shows `file://` pages as static snapshots (no scripts), so serve the folder over `http://localhost` instead. There's no Python or Node on this PC; a small PowerShell `HttpListener` script works. `.claude/launch.json` is git-ignored and may point to a script from an old session — recreate it if it's missing.
  - The pane's `localhost` data is separate from the user's Chrome (`file://`) data, so you can't see the user's own plan there. Ask them to export a backup if a check needs their real data.
  - When a test snippet changes `Store.data`, back up `localStorage.getItem('gitfit-data')` first and restore it after, or switch `Store.save` off while previewing. Many functions take a `now` time (e.g. `Streak.update(now)`) so weeks can be faked.
  - The red `manifest.json` CORS errors when opening `index.html` from a file are harmless; it loads fine on GitHub Pages.
  - For the user to preview things themselves, give a temporary console snippet (not in the project) with simple `preview.…()` commands and a `preview.done()` that reloads. Remind them Chrome needs `allow pasting` typed once.
- Design for iPhone Safari: touch targets, the `inputmode="decimal"` keyboards, safe areas / status bar (see the comments in `index.html` about `black` vs `black-translucent`), and numbers typed with a comma (`parseNumber()` handles `62,5`).
- New screens: a function in `views.js` returning `{ title, back, html }` plus a route in `app.js`. New tabs: `TABS` in `tabs.js`. New settings: default in `DEFAULT_SETTINGS`, a field in `Views.settings()`, and a line in `saveSettingsForm()` in `app.js`.
- New built-in exercises: add a line to `LIBRARY` in `library.js` using existing muscle ids; add standards in `standards.js` only from the published source.
- Keep code style consistent with the existing files: plain functions and objects, comments explaining "why" in plain English.
- Git is at `C:\Program Files\Git\cmd\git.exe`. Pushing needs a GitHub sign-in prompt, so when the user asks for a push, run `git push` in their Terminal panel rather than a background shell. After pushing, tell them GitHub Pages takes a minute or two and to fully close and reopen the home-screen app if it still looks old.
- Animations: only `transform`/`opacity` (smooth on iPhone Safari), no libraries, and turn them off under `prefers-reduced-motion`.
- Files use LF line endings; git's "LF will be replaced by CRLF" warnings are normal.
